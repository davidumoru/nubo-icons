# Coherent rules and distribution decide which icon sets win

The best open-source icon sets do not have the cleverest drawings. They have a short, numeric, enforced rulebook (canvas, stroke, corners, spacing, metaphor), metadata and tooling that keep thousands of glyphs consistent, and a distribution channel that makes them the default. Lucide shows this most clearly. It is a community fork of Feather with almost the same look, but open governance and its place as the default icon set in shadcn/ui carried it to about **108 million weekly npm downloads**, more than 20x any other dedicated set, while Feather, which still has more GitHub stars, stalled under a single inactive maintainer ([Lucide comparison](https://lucide.dev/guide/comparison); [npm API](https://api.npmjs.org/downloads/point/last-week/lucide-react); [GitHub API](https://api.github.com/repos/feathericons/feather)). On the design side, the major systems agree on a lot: a 24px canvas with about 2px padding, one stroke weight per set, keyline shapes that even out optical size, front-on views with no perspective, minimum detail, and metaphors named for what they depict. On the engineering side, every serious set treats a folder of SVGs as the single source of truth and generates a package per framework from it, with SVGO cleanup, schema-validated metadata, one ESM module per icon for tree-shaking, `currentColor`, and `aria-hidden` by default. The open market space is real but narrow. The 2px round-cap "Feather look" is everywhere, and people complain that icon libraries are hard to tell apart. A new set like nubo-icons should therefore pick one or two deliberate, documented visual traits, stay drop-in compatible with Lucide's API and names, and treat accessibility defaults, metadata and Iconify/shadcn distribution as part of the product, not afterthoughts.

## A 24px canvas and one stroke decision set most of a set's character

Most UI icon sets sit on the same geometry, inherited from Material's original system-icon spec. Icons display at 24dp inside a 20×20 live area. Keyline shapes compensate for optical size: a **20dp circle, an 18dp square, and 16×20 / 20×16 rectangles**, so that a circle and a square look equally large. Content may push into the padding only "if additional visual weight is needed" ([Material Design v1 Icons](https://m1.material.io/style/icons.html)). Lucide, Feather, Tabler and Heroicons all use a 24px canvas. Lucide's spec requires strokes to sit at least 1px from the edge, which places a centered 2px stroke's geometry 2px in ([Lucide specification](https://github.com/lucide-icons/lucide/blob/main/docs/contribute/icons/specification.md)). Dense product systems use 16px instead. GitLab draws at 16px with a 14×14 live area and 1px padding, and Atlassian uses a 16×16 box ([GitLab Pajamas](https://design.gitlab.com/product-foundations/iconography); [Atlassian Iconography](https://atlassian.design/foundations/iconography)). IBM is an outlier: it draws at 32px and scales down linearly ([IBM UI icons: Design](https://www.ibm.com/design/language/iconography/ui-icons/design/)). Phosphor is also unusual. It is designed at 16×16 "to read well small and scale up big" but authored on a 256-unit viewBox ([Phosphor README](https://github.com/phosphor-icons/homepage)). Every system treats keylines as guides, not limits. IBM says "Don't force the content to fit inside the key shapes", and GitLab calls its grid "a starting point and guide, but not a hard rule".

The stroke decision matters more than any other, because it determines how the set looks and also how it is built. At 24px the field splits in two. Material, IBM, Lucide, Feather and Tabler use **2px**. Heroicons v2, Iconoir and (at 16px) GitLab and Atlassian use **1.5px**. GitLab picked 1.5px because it is "similarly weighted to regular system font weights at body text sizes" ([GitLab Pajamas](https://design.gitlab.com/product-foundations/iconography); [Heroicons SVG](https://unpkg.com/heroicons@2.2.0/24/outline/academic-cap.svg)). The arithmetic shows why this matters at small sizes. A 2px stroke drawn at 24 renders at 1.33px when the icon is shown at 16px, which is why Lucide looks heavier than Phosphor at small sizes ([elmeragroup/fuse PR #207](https://github.com/elmeragroup/fuse/pull/207)). A 1.5px stroke at 24 renders at exactly 1px at 16. Cap and join shape is the cheapest strong personality signal. Lucide requires round caps and joins, and Feather, Tabler and GitLab use them too, which reads as friendly. Material forbids "rounded stroke terminals". IBM borrows "square caps", "slab characteristics" and "rounded exteriors with 90° interiors" from IBM Plex. Atlassian pairs rounded corners with square caps to "add boldness" ([Lucide design principles](https://github.com/lucide-icons/lucide/blob/main/docs/contribute/icons/design-principles.md); [Material v1](https://m1.material.io/style/icons.html); [IBM](https://www.ibm.com/design/language/iconography/ui-icons/design/)). GitLab gives the most careful rule. Joins should follow meaning: a checkmark is one continuous object and gets a round join, while clock hands are two joined objects and get a miter. Square caps can signal clipping or layering.

Corners and angles are almost standardized. A **2px exterior radius** is close to universal. Lucide drops to 1px for elements under 8px and uses about 2.41px (1+√2) where diagonals meet at 90°, so the arc stays on the grid. Interior corners stay sharp, and so do corners "where multiple lines meet" ([Lucide spec](https://github.com/lucide-icons/lucide/blob/main/docs/contribute/icons/specification.md)). IBM and GitLab both use 15° angle increments. IBM favors 45° for even anti-aliasing but warns "Don't use 45° angles exclusively… It won't work." For spacing, Lucide requires at least 2px between separate elements (a 2px circle must fit in every gap). GitLab accepts 1px and says to close any counter smaller than that.

On pixel snapping the systems split by stroke philosophy. IBM bans decimals in coordinates, never uses center borders, and expands strokes into outlines before delivery. Lucide keeps live centered strokes and states that "pixel alignment should not take precedence over the visual quality of the icon." GitLab takes a middle path: closed shapes snap to whole pixels, but curves and diagonals may go off-grid "to feel natural rather than forced" ([IBM Contribute](https://www.ibm.com/design/language/iconography/ui-icons/contribute/); [GitLab](https://design.gitlab.com/product-foundations/iconography)). Real optical sizing means redrawing, not scaling. Fluent ships separate drawings at 12, 16, 20, 24, 28, 32 and 48. Heroicons draws separate 24, 20 and 16 masters. Octicons draws 16 and 24 separately. Material Symbols handles it with a variable-font `opsz` axis that "automatically adjust[s] the stroke weight" as size changes ([Fluent metadata](https://raw.githubusercontent.com/microsoft/fluentui-system-icons/main/assets/Add%20Circle/metadata.json); [Heroicons](https://github.com/tailwindlabs/heroicons); [Google Fonts Material Symbols guide](https://developers.google.com/fonts/docs/material_symbols)).

## Good icons sit close to their meaning, and very few are universal

Usability research is clear about what icons can and cannot do. Nielsen Norman Group finds that only a handful of icons are close to universal (home, print, magnifying-glass search). Hearts and stars mean different things on different sites, and a clock used to mean "history" went unclicked by every participant ("Obscure icon = wasted feature"). Its rule of thumb: if it takes more than 5 seconds to think of an icon for a concept, the icon will probably not communicate it. Its headline advice is that **"icon labels should be visible at all times"** ([NN/g Icon Usability](https://www.nngroup.com/articles/icon-usability/)). NN/g's hidden-navigation study shows what icon-only interfaces cost. On desktop, people used navigation in 27% of cases when it was hidden behind a hamburger, against 48% when visible, and tasks took at least 39% longer ([NN/g Hamburger Menus](https://www.nngroup.com/articles/hamburger-menus/)). These studies date from 2014–2016, and hamburger recognition has probably improved since. No newer replication was found.

The academic work points to which design levers matter. McDougall and Isherwood found that **semantic distance**, meaning how directly the picture maps to the function, explained up to 55% of the variance in early identification. Familiarity took over as users learned the mappings, and concreteness mattered less than designers tend to assume ([Bournemouth profile](https://staffprofiles.bournemouth.ac.uk/display/journal-article/11112)). Newer work from Jyväskylä found concreteness only weakly predicted semantic distance, and that familiarity with an icon's _style_ was the strongest predictor of how attractive people found it ([JYX repository](https://jyx.jyu.fi/bitstreams/1380583d-520f-4c32-b02d-c08cd70a058a/download)). That second finding cuts both ways. Looking like Lucide earns a familiarity bonus, and departing from it costs some. For an icon set, the evidence says to favor direct metaphors over realism or detail, to follow conventions users already know, and to design on the assumption that icons will appear next to labels.

Mature systems turn this into metaphor policy. Fluent names icons "for the shape or object they depict, not the function they perform (e.g., 'Shield,' not 'Security')" ([Fluent 2](https://fluent2.microsoft.design/iconography)). Lucide makes the same rule: names describe what the icon shows. It keeps `save` only for legacy reasons and tags it "floppy disk" ([Lucide naming conventions](https://github.com/lucide-icons/lucide/blob/main/docs/contribute/icons/naming-conventions.md)). This splits two decisions cleanly. The drawing answers "what does it look like", and search tags answer "what can it mean", so one glyph can serve several meanings. GitLab adds "specific meaning, specific icon" (don't reuse one icon for unrelated concepts), prefers modern objects to antiquated ones, and asks for metaphors that are not violent ([GitLab Pajamas](https://design.gitlab.com/product-foundations/iconography)). The floppy disk shows where these rules collide. Critics have called it obsolete since 2011, and defenders argue that "80% of users recognizing the floppy is better than 100% of users wondering what a downward arrow means." No current recognition data settles it ([Thomas Park](https://thomaspark.co/2011/04/save-icon/); [UX Movement](https://uxmovement.com/buttons/why-the-floppy-disk-icon-for-save-must-die/)). In practice, entrenched conventions beat literal accuracy.

Consistency within a set comes from a small variant matrix and reused parts. Fluent uses Regular for wayfinding and Filled for selected states. Its modifiers are "always filled" and "always bottom-right". Lucide requires modifiers to keep "consistent geometry, size, and placement across related icons", and names them `<group>-<variant>` (`badge-plus`, `circle-check`). Iconoir's convention is `[Object]-[Modifier]-[Container]`, with object nouns preferred over actions (`user-minus`, not `remove-user`) ([Fluent 2](https://fluent2.microsoft.design/iconography); [Lucide spec](https://github.com/lucide-icons/lucide/blob/main/docs/contribute/icons/specification.md); [Iconoir NAMING_CONVENTION](https://github.com/iconoir-icons/iconoir/blob/HEAD/NAMING_CONVENTION.md)). Every system bans perspective. IBM asks for "straight-on or profile views", Atlassian says "Don't use diagonal perspectives to create 3D shapes", and Material says "Don't tilt, rotate, or make icons appear dimensional." Every system also limits detail. Lucide omits "details that are not necessary for recognition", Atlassian asks for the "minimum detail required to express a metaphor", and Lucide's "blur test" flags dark clumps as excess detail ([Lucide design guide](https://lucide.dev/contribute/icon-design-guide)).

Process at the big systems follows the same path. Designers first search for an existing icon, then write a brief with the usage context, sketch, and draw on a template. Review happens in context and at small sizes, followed by production cleanup and metadata. IBM lets non-designers submit sketches as GitHub issues, and review "can take up to 30 days" ([IBM Contribute](https://www.ibm.com/design/language/iconography/ui-icons/contribute/)). Tatsiana Tarkan recommends putting each new icon into a real UI next to existing elements, trying several stroke weights, assigning one owner designer, and tracking status (finished, needs improvement, redraw). She calls icons "the most visually volatile part of a design system" ([Smashing Magazine 2024](https://www.smashingmagazine.com/2024/04/iconography-design-systems-troubleshooting-maintenance/)). NN/g's testing method is cheap and repeatable. Show the icon and ask what it means to test recognizability, then ask the same people again a couple of weeks later to test memorability.

## Taste is a short enforced rulebook plus explicit permission to break it

When practitioners and system docs describe what separates great sets from mediocre ones, they describe coherence, not individual brilliance. Lucide's principles say it "is a consistent icon set, not a collection of unrelated icons. Every icon should feel like it belongs with the rest." IBM says "no icon should appear heavier or lighter than another". GitLab warns that unbalanced icons "draw unnecessary attention to themselves, or seemingly disappear" ([Lucide design principles](https://github.com/lucide-icons/lucide/blob/main/docs/contribute/icons/design-principles.md); [IBM](https://www.ibm.com/design/language/iconography/ui-icons/design/); [GitLab](https://design.gitlab.com/product-foundations/iconography)). The best rulebooks also include an override clause. GitLab says "Clarity should always override consistency", and Lucide says "Consistency should not override clarity, balance, or readability." A Feather contributor admitted breaking the constraints on the RSS icon because "it looks much nicer this way" ([HN: Feather](https://news.ycombinator.com/item?id=33223964)). Taste, in this sense, is an exact rulebook combined with trained judgment about when to depart from it.

The strongest personalities come from a parent system rather than from ornament. IBM's icons carry IBM Plex's slab tips and square caps. Atlassian's corner radii follow its typography. GitLab lists "a touch of personality" as border radius and open counters ([IBM](https://www.ibm.com/design/language/iconography/ui-icons/design/); [Atlassian](https://atlassian.design/foundations/iconography)). The common failures are mixed styles, mixed sizes and missing source files ([Smashing 2024](https://www.smashingmagazine.com/2024/04/iconography-design-systems-troubleshooting-maintenance/)). Users also notice semantic errors. Hacker News commenters criticized scissors whose finger holes are too big to cut and butterflies drawn as "dead" pinned specimens, and noted that a Lucide duplicate (`signal-zero` and `signal-low`) took six months to fix. The loudest complaint is sameness: "the whole web has come to the conclusion that icons have to be monochrome and boring," and "it's so hard to tell the difference between all the different icon libraries" ([HN: Feather](https://news.ycombinator.com/item?id=33223964)).

The market has two clusters, and very little open space lies between them.

Download numbers mostly measure distribution, not preference. Lucide's lead comes from being the shadcn/ui default since **November 2024**, when the new-york style switched from Radix Icons ([shadcn changelog](https://ui.shadcn.com/docs/changelog/2024-11-icons)). Radix's 5.2M weekly downloads for a frozen 318-icon set are leftover installs from before that switch. The history of Feather and Lucide shows how much governance matters. Feather "had more than 300 open issues and over 100 open pull requests" with no realistic chance of merging, so Lucide forked to "grow the icon set while keeping Feather's minimalist style" under community control ([Lucide comparison](https://lucide.dev/guide/comparison); [Feather #1110](https://github.com/feathericons/feather/issues/1110)). Money is thin in pure open source. Lucide's OpenCollective brings in about €3,000 a year and Iconoir's about $265 ([OpenCollective](https://opencollective.com/lucide-icons.json); [OpenCollective](https://opencollective.com/iconoir.json)). The sustainable models are a corporate parent (Google, Microsoft, GitHub, Tailwind) or an open-core free tier (Hugeicons, Untitled UI, Tabler's $9/$69 bundles).

Governance runs from closed to open, and each position has costs. Heroicons accepts no new icons, which caps it at about 324 per style but protects its taste ([Heroicons README](https://github.com/tailwindlabs/heroicons)). Iconoir, Remix and Material refuse icon PRs and take requests through issues ([Iconoir CONTRIBUTING](https://github.com/iconoir-icons/iconoir/blob/HEAD/CONTRIBUTING.md)). Lucide accepts community icons, which works only because it has a numeric guide, strong reviewer-maintainers, and tooling. Simple Icons avoids "why wasn't my icon added" fights with objective popularity thresholds, a forbidden-brands list and a mandatory AI-use disclosure ([Simple Icons CONTRIBUTING](https://github.com/simple-icons/simple-icons/blob/develop/CONTRIBUTING.md)). Brand logos are now widely excluded. Lucide v1 removed them over "increasing legal pressures", and Iconoir and Material exclude them too ([Lucide v1](https://github.com/lucide-icons/lucide/blob/main/docs/guide/version-1.md)). Licensing deserves one warning. Since January 2026, Remix Icon's custom license prohibits use in "competing icon libraries", so a new set cannot borrow its glyphs, even modified ([Remix License](https://github.com/Remix-Design/RemixIcon/blob/HEAD/License)).

## Accessibility is mostly a property of component defaults, not glyphs

Five WCAG 2.2 criteria apply directly to icons. Under **1.1.1**, meaningful icons need a text alternative and decorative ones must be hidden from assistive technology. Under **1.4.11**, icons needed to understand content or identify a control need **3:1 contrast**; for a single-color icon, "the entire image is a graphical object". Under **2.5.8**, targets must be at least **24×24 CSS px** or adequately spaced. **1.4.1** forbids conveying meaning by color alone. **4.1.2** requires icon buttons to have a name, role and value ([W3C 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html); [W3C 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html); [W3C 1.1.1](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html)). Label in Name (2.5.3) does not apply to pure icon buttons, because they have no visible text label ([W3C 2.5.3](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html)). WCAG 3.0 is still a Working Draft, with a Recommendation projected no earlier than 2028, so 2.2 remains the compliance baseline ([W3C WCAG 3.0 WD](https://www.w3.org/TR/2026/WD-wcag-3.0-20260303/); [AbilityNet](https://abilitynet.org.uk/resources/digital-accessibility/what-expect-wcag-30-web-content-accessibility-guidelines)). A library cannot make a site compliant, because contrast, target size and naming depend on how the icon is used. It can make the compliant path the default. Two parts of that are the set's own decisions: stroke weight and default color. Hairline strokes in light grey are the easiest way to fail 1.4.11.

Implementation research agrees on one pattern. Icons are decorative by default, and the _control_ gets the name. Sara Soueidan ranks the options for icon-only buttons. Visually hidden text inside the button comes first, `aria-labelledby` second, and `aria-label` on the button third, with the SVG kept `aria-hidden="true"` in all three. Naming the SVG itself "come[s] with failures in some browser / screen reader combinations" ([Sara Soueidan](https://www.sarasoueidan.com/blog/accessible-icon-buttons/)). Scott O'Hara documented a `role="img"` SVG with an `aria-label` failing inside links in IE11+NVDA and Edge+JAWS. He also warns that an unhidden SVG may be announced as an unnamed "group", and that junk `<title>` elements exported by design tools reach screen readers and tooltips ([Scott O'Hara](https://www.scottohara.me/blog/2019/05/22/contextual-images-svgs-and-a11y.html)). Libraries handle this differently:

| Library     | Default                                            | Meaningful mode                                             | Notes                                               |
| ----------- | -------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------- |
| Lucide (v1) | `aria-hidden="true"` unless an a11y prop is passed | Pass `aria-label`/`title`                                   | Docs: label the button, not the icon                |
| MUI SvgIcon | `aria-hidden`, `focusable="false"`                 | `titleAccess` sets `role="img"` + `<title>`, removes hidden | Cleanest single-prop switch                         |
| Heroicons   | `aria-hidden="true"`, `data-slot="icon"`           | `title` prop renders `<title>`                              | `aria-hidden` persists unless overridden; a pitfall |
| Phosphor    | No hiding                                          | `alt` renders `<title>` (no `role`)                         | Has `mirrored` prop for RTL                         |
| Radix       | No a11y attributes                                 | Consumer's job                                              | Plain `<svg>`                                       |

Sources: [Lucide accessibility guide](https://lucide.dev/guide/advanced/accessibility); [MUI SvgIcon source](https://unpkg.com/@mui/material/SvgIcon/SvgIcon.js); [Heroicons source](https://unpkg.com/@heroicons/react@2/24/outline/esm/HomeIcon.js); [Phosphor source](https://unpkg.com/@phosphor-icons/react/dist/lib/SSRBase.es.js); [Radix source](https://unpkg.com/@radix-ui/react-icons/dist/react-icons.esm.js).

The surrounding decisions all favor inline SVG. GitHub dropped the Octicons icon font in 2016 for concrete reasons. Fonts rendered blurry on 1x screens, caused a flash of unstyled content, showed empty squares to users who override fonts (for example dyslexic readers), and allowed only one drawing per glyph. SVG also brought accessible labels and animation, with no pageload penalty ([GitHub Blog](https://github.blog/engineering/user-experience/delivering-octicons-with-svg/)). `currentColor` fills and strokes let single-color icons follow forced-colors (Windows High Contrast) mode. Browser behavior differs, though, and multi-color icons need an explicit `@media (forced-colors: active)` override ([MDN forced-colors](https://developer.mozilla.org/docs/Web/CSS/@media/forced-colors); [csswg #6310](https://github.com/w3c/csswg-drafts/issues/6310)). For right-to-left languages, Material's rule is to mirror icons that communicate direction (back and forward above all) and never to mirror media playback, clocks, numbers or charts, because "the direction of these elements represents the direction of the tape, not the direction of time" ([Material bidirectionality](https://m2.material.io/go/design-bidirectionality)). Fluent puts this in its metadata, marking each icon `mirror` or `unique` ([Fluent repo](https://github.com/microsoft/fluentui-system-icons)). A blanket CSS flip of every SVG in `[dir=rtl]` is therefore wrong, and the information belongs in per-icon data. Animated icons fall under 2.2.2 (a pause mechanism for motion longer than 5 seconds) and should honor `prefers-reduced-motion` ([W3C 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)).

## Every serious set compiles one SVG folder into many generated packages

The architecture is consistent across projects. A folder of SVGs is the source of truth. A normalization and validation step enforces the spec. A codegen step turns each SVG into a framework-neutral "icon node" (Lucide and Tabler use `[tag, attrs]` arrays), and per-framework templates wrap that node in a small shared base component. Each icon becomes its own ESM module, so bundlers tree-shake everything an app doesn't import. The projects differ mainly in where metadata lives, how much is validated, and how releases happen.

**Lucide** is the most reusable model. It is one pnpm monorepo. Paired `icons/<name>.svg` and `icons/<name>.json` files sit at the root, and `packages/` holds about a dozen framework packages (react, vue, svelte, solid, angular, astro, preact, react-native, vanilla, static). `tools/` contains a generic `build-icons` codegen CLI driven by per-package `exportTemplate.mts` files, a framework-agnostic `@lucide/shared` builder, a font builder and shared Rollup plugins. `integrations/` holds real Next.js, Vite, React Router and TanStack apps tested with Playwright ([Lucide repo](https://github.com/lucide-icons/lucide); [build-icons CLI](https://github.com/lucide-icons/lucide/blob/main/tools/build-icons/cli.ts)). Each icon's JSON is validated against a JSON Schema (draft 2020-12, `additionalProperties: false`). Required fields are contributors, tags, categories (an enum of 42) and use-cases. Aliases carry `deprecated`, `deprecationReason` and `toBeRemovedInVersion` ([icon.schema.json](https://github.com/lucide-icons/lucide/blob/main/icon.schema.json)). A custom Prettier plugin runs SVGO with a per-element attribute allowlist (a `path` may carry only `d`) and rewrites the root `<svg>` to a canonical header, so `prettier --check` doubles as the icon linter ([prettier-plugin-lucide-svg](https://github.com/lucide-icons/lucide/blob/main/prettier-plugin-lucide-svg.mjs)). Generated React modules include a base64 JSDoc `@preview` image, so the IDE shows the icon on hover, and an `@deprecated` tag for renamed icons. The `Icon` base adds `aria-hidden` unless an accessibility prop is present, and supports `nonScalingStroke` via `vector-effect` ([exportTemplate](https://github.com/lucide-icons/lucide/blob/main/packages/lucide-react/scripts/exportTemplate.mts); [Icon.ts](https://github.com/lucide-icons/lucide/blob/main/packages/lucide-react/src/Icon.ts)). Lucide v1 dropped UMD builds from lucide-react, which its notes say cut the package from 11.4 MB to 1 MB. The same page labels this a 32.3% reduction, so the two figures conflict ([Lucide v1](https://github.com/lucide-icons/lucide/blob/main/docs/guide/version-1.md)).

**Tabler** adds the tooling a 6,000-icon set needs. Turborepo caches builds keyed on `icons/**` and the build scripts. pnpm catalogs pin shared dependency versions, and `minimumReleaseAge: 10080` refuses dependencies published less than a week ago. Changesets run with every package in one fixed version group ([turbo.json](https://github.com/tabler/tabler-icons/blob/main/turbo.json); [pnpm-workspace.yaml](https://github.com/tabler/tabler-icons/blob/main/pnpm-workspace.yaml); [changeset config](https://github.com/tabler/tabler-icons/blob/main/.changeset/config.json)). Its validator is strict. Paths only (no `<circle>`, `<rect>` or `<g>`), `stroke-width` only on the root, no closepath in outline icons, no degenerate segments, and unique 4–5-digit hex codepoints. An `import.mjs` step takes designer exports from `new/`, converts dashes to paths, rejects transforms, and strips Figma and Sketch residue ([validate-icons.mjs](https://github.com/tabler/tabler-icons/blob/main/.build/validate-icons.mjs); [import.mjs](https://github.com/tabler/tabler-icons/blob/main/.build/import.mjs)). Tabler keeps metadata as YAML front matter inside an HTML comment at the top of each SVG, which means one file per icon but requires custom parsing. It also uses a declaration-bundling trick that emits one `.d.ts` instead of thousands, and runs PR builds with `ICONS_LIMIT=100` to keep CI fast.

**Phosphor** shows the costs of the multi-repo model. `core` holds raw stroked SVGs and flattened fill-only assets for six weights, plus a catalog generated from a private metadata API. Each framework repo pulls `core` in as a git submodule ([Phosphor core](https://github.com/phosphor-icons/core); [react .gitmodules](https://github.com/phosphor-icons/react/blob/main/.gitmodules)). Tooling drifts between repos: the Vue repo has both npm and yarn lockfiles and pins older Vite and TypeScript. Publishing is manual, and versions are out of step: `core` at 2.1.1 from 2024, `react` at 2.1.10 from 2025 ([npm registry](https://registry.npmjs.org/@phosphor-icons/react)). Its React package also bundles all six weights into every icon module as a `Map<weight, element>`, which is convenient for a runtime `weight` prop but heavier per icon.

Smaller sets contribute individual techniques worth copying. Heroicons keeps one SVGO config per style, which injects `stroke-width="1.5"`, `currentColor`, `aria-hidden` and `data-slot="icon"`. It generates its `exports` map, publishes an `0.0.0-insiders.<sha>` build on every push, and marks deprecated icons with `@deprecated` instead of removing them ([svgo.24.outline.mjs](https://github.com/tailwindlabs/heroicons/blob/HEAD/svgo.24.outline.mjs); [build.js](https://github.com/tailwindlabs/heroicons/blob/HEAD/scripts/build.js)). Octicons validates size against the filename (`name-16.svg` must have height 16) and stores **SHA-256 "protected geometry" fingerprints**, so a rename cannot silently swap a glyph. Its CI auto-commits SVGO output on PRs, it runs tree-shaking and code-splitting tests with `publint --strict`, and it ships an `AGENTS.md` plus an icon-review skill for AI-assisted triage ([icon-metadata.json](https://github.com/primer/octicons/blob/HEAD/icon-metadata.json); [optimize.yml](https://github.com/primer/octicons/blob/HEAD/.github/workflows/optimize.yml); [AGENTS.md](https://github.com/primer/octicons/blob/HEAD/AGENTS.md)). Simple Icons sets the bar for validation: an svglint config with about 13 custom path rules (precision, collinear segments, centering), a JSON Schema, and CI that fails any hand-edit of generated files. It also has the clearest written semver policy. Removals and renames are major, additions are minor, and redraws are patch. Minor and patch releases ship weekly, and majors come about every six months to batch removals ([svglint config](https://github.com/simple-icons/simple-icons/blob/HEAD/svglint.config.mjs); [VERSIONING.md](https://github.com/simple-icons/simple-icons/blob/HEAD/VERSIONING.md)).

Releases and supply chain have converged on automation. Lucide publishes a new **minor** whenever icon SVGs have changed since the last tag. A daily cron or a push to main triggers it, behind a GitHub Environment approval gate, and every package is published at one version with npm OIDC provenance. Package versions in git stay at `0.0.1`, and the real version is injected at release time ([ci.yml](https://github.com/lucide-icons/lucide/blob/main/.github/workflows/ci.yml); [release.yml](https://github.com/lucide-icons/lucide/blob/main/.github/workflows/release.yml)). Tabler auto-generates a changeset for any new icon, so additions always bump the minor, and publishes through npm trusted publishing ([Tabler release.yml](https://github.com/tabler/tabler-icons/blob/main/.github/workflows/release.yml)). Both projects use the same fork-safe pattern for visual PR previews. An unprivileged `pull_request` job renders the changed icons to a markdown artifact, and a privileged `workflow_run` job posts it as a comment ([Lucide preview workflow](https://github.com/lucide-icons/lucide/blob/main/.github/workflows/pull-request-icon-preview.yml); [Tabler validate-pr](https://github.com/tabler/tabler-icons/blob/main/.github/workflows/validate-pr.yml)). Lucide also pins every Action to a full commit SHA. None of the three large sets enforces a bundle-size budget in CI. They only emit `rollup-plugin-visualizer` reports, so there is room to do better.

Distribution beyond npm is dominated by **Iconify**. `@iconify/json` mirrors about 230 sets and updates "several times a week". It feeds `unplugin-icons` (Vite, Webpack, Rspack, Nuxt, and compilers for Vue, React, Svelte, Solid, Astro and more) and the Tailwind 4 plugin's `icon-[prefix--name]` classes ([Iconify icon-sets](https://github.com/iconify/icon-sets); [unplugin-icons](https://github.com/unplugin/unplugin-icons); [Iconify Tailwind 4](https://iconify.design/docs/usage/css/tailwind/tailwind4/)). To be included, a set needs an open-source license and a git or npm source Iconify can download automatically ([Iconify CONTRIBUTING](https://github.com/iconify/icon-sets/blob/HEAD/CONTRIBUTING.md)). For a new set this is the cheapest way to reach a dozen ecosystems without maintaining packages for each. Icon fonts survive mainly as opt-in extras: Tabler's webfont at three stroke weights, Lucide's font with stable codepoints, and Simple Icons' font repo released in lockstep by dispatch. Stroke-based sets must outline their strokes before generating a font (Lucide uses `oslllo-svg-fixer`, Tabler uses `unstroke`) ([Lucide build-font](https://github.com/lucide-icons/lucide/blob/main/tools/build-font/package.json); [Tabler build-webfont](https://github.com/tabler/tabler-icons/blob/main/packages/icons-webfont/.build/build-webfont.mjs)).

## The website is a search engine with a customizer and a metadata API

No single site stack dominates, but the best sites live inside the icon monorepo. Lucide's site is VitePress plus a Nitro API on Vercel in `docs/`. A dozen `prebuild` scripts generate icon nodes, a metadata index, release history read from git, related icons, popularity data and per-icon OG images rendered with `sharp` ([Lucide docs package.json](https://github.com/lucide-icons/lucide/blob/main/docs/package.json); [createOGImage.ts](https://github.com/lucide-icons/lucide/blob/main/docs/.vitepress/createOGImage.ts)). Iconoir's site is a Next.js 15 static export inside its repo, served from GitHub Pages ([iconoir.com package.json](https://github.com/iconoir-icons/iconoir/blob/main/iconoir.com/package.json)). Phosphor's is a separate React 19 and Vite SPA, Heroicons and Tabler run closed-source Next.js sites on Vercel, and Simple Icons has moved to a Rust/WASM app that streams about 2.4 MB of WebAssembly behind a loader ([Phosphor homepage](https://github.com/phosphor-icons/homepage/blob/master/package.json); [simple-icons-website-rs](https://github.com/simple-icons/simple-icons-website-rs/blob/master/Cargo.toml)). A site in the monorepo can import the in-repo packages directly and derive everything (version history, contributors, categories) from the source files at build time. That is the decisive advantage.

Users now expect a fixed set of features. The first is instant fuzzy search over names, tags and categories. Lucide uses Fuse.js at `threshold: 0.2` and splits the query into tokens that must all match. Phosphor weights the name at 4 against tags and categories ([Lucide useSearch.ts](https://github.com/lucide-icons/lucide/blob/main/docs/.vitepress/theme/composables/useSearch.ts); [Phosphor state](https://github.com/phosphor-icons/homepage/blob/master/src/state/index.ts)). Next comes a live customizer for color, stroke width, size and non-scaling stroke, then one-click copy of SVG or JSX, category filters and dark mode. The leading sites go further. Lucide's per-icon pages show the version an icon was created in, the version it last changed in, contributor avatars, related icons and an "Edit in studio" link. Phosphor keeps all settings in the URL so a shared link reproduces the view, and offers `*new*` and `*updated*` pseudo-tags. Icônes lets users collect icons in a "bag" and pack them into a custom font or zip ([lucide.dev/icons/house](https://lucide.dev/icons/house); [Icônes](https://github.com/antfu-collective/icones)). Large sets virtualize the grid. Lucide chunks results into rows with `useVirtualList`, and Iconoir uses `react-window`. Heroicons, with about 316 icons, server-renders all of them into roughly 400 KB of HTML, which works only for small sets ([Lucide IconsOverview.vue](https://github.com/lucide-icons/lucide/blob/main/docs/.vitepress/theme/components/icons/IconsOverview.vue)).

Machine-facing surfaces are the open frontier. Lucide alone publishes a real `llms.txt`, generated by `vitepress-plugin-llms`. Phosphor, Tabler, Iconoir, Remix, Radix and Simple Icons all returned 404 when checked on 2026-10-09. MCP servers for Lucide and Iconify exist only as community projects, and **none of the ten projects examined ships an official MCP server** ([lucide.dev/llms.txt](https://lucide.dev/llms.txt); [lucide-icons-mcp](https://mcpservers.org/servers/SeeYangZhi/lucide-icons-mcp)). Lucide also exposes `/api/icon-nodes`, `/api/tags` and `/api/figma` routes that serve its Figma plugin and external tools. Marketing patterns are modest and reusable: a positioning line, a live icon count, a comparison page against rival sets (Lucide's `comparison.md`), a showcase, and sponsor badges or Carbon ads.

## A recommended blueprint for nubo-icons

This section turns the evidence into decisions. It is opinionated by design, and where a choice is a judgment rather than an established practice, it says so.

### Design spec: proven geometry, one signature, a lighter line

Use the standard geometry so nubo can drop into any layout built for Lucide, Tabler or Heroicons: a **24×24 canvas, 2px padding, a 20×20 live area**, and Material's keylines (circle 20, square 18, rectangles 16×20 and 20×16). Draw **1.5px centered strokes with round caps and round joins**. The research supports this as nubo's main point of difference. The 1.5px look belongs either to a closed set (Heroicons, about 324 icons per style) or to a thinly funded one (Iconoir, about $265 a year), so an actively governed, high-craft 1.5px set has a real gap to fill. The weight also renders at exactly 1px at 16px, while 2px renders at a soft 1.33px. Ship `strokeWidth` as a runtime prop so teams that want to match Lucide can set 2. The trade-off is accessibility. Thinner lines lose effective contrast sooner, so the docs should recommend text-strength colors for icons and warn against light-grey icon styling under WCAG 1.4.11.

Take the corner rules directly from Lucide: 2px radius on elements of 8px or more, 1px below that, about 2.41px where diagonals meet at 90°, and sharp corners where several lines meet. Use angles in 15° increments with 45° preferred, keep at least 2px between separate elements, and allow coordinates on a 0.5 grid but put visual quality ahead of snapping. Give nubo one documented signature that follows from the name "nubo" (cloud). One option is a slightly softer, cloud-derived curvature rule for container shapes (badge circles, rounded rectangles) applied the same way everywhere. Keep it subtle enough to pass the "belongs with the set" test. This is a taste call, not a finding. The evidence only says that personality should come from one rule applied consistently, not from ornament.

Before drawing more than a handful of icons, write a **canonical parts library**: document, person, gear, cloud, badge circle, plus, check, slash and arrowheads, each with fixed size and placement. Fix the modifier rules too. Modifiers go bottom-right, have a set badge diameter and a set cutout gap, and the slash has a set angle and direction. No source provides numeric slash or badge geometry, so nubo has to define these itself, and they matter most for keeping variants consistent. Name icons by what they depict, not what they do. Use Lucide-compatible names where the concepts match, and Iconoir's `object-modifier-container` order otherwise. Launch with a single outline style. Add a filled style later as a separate, parity-checked directory (the Heroicons and Tabler model), not as a six-weight matrix. Weights multiply design and review work per icon and inflate module size, and both costs are unaffordable for a new project. Decide on a separately drawn 16px set only once real dense-UI demand appears. Octicons and Heroicons show that it means a second drawing of every icon.

Write the spec in Lucide's must/should form, publish it in the repo, and back each "must" with a lint rule. Add a scope policy in the style of Simple Icons. It should say that nubo covers UI concepts, ships **no brand logos** (the legal exposure that pushed Lucide v1 and Iconoir to drop them), and excludes violent metaphors. It should also name the antiquated-but-entrenched conventions nubo will keep, such as the floppy disk for save, tagged by its literal name. Build a review ritual from the evidence. Check each icon at 16, 20 and 24px against text. Run a blur test for weight. Place it next to its neighbors in a sample UI. Apply the 5-second metaphor rule, and run a quick NN/g-style "what does this mean?" test for anything outside the well-known core.

### Repository architecture: Lucide's split, Tabler's guardrails

Use a single pnpm monorepo with SVG sources at the root and generated packages beside them:

```
nubo-icons/
├── icons/                 # <name>.svg + <name>.json (source of truth)
├── categories/            # <slug>.json, schema-validated
├── schemas/               # icon.schema.json, category.schema.json
├── tools/
│   ├── build-icons/       # codegen CLI: SVG → IconNode → per-framework template
│   ├── svg-lint/          # validator + SVGO/Prettier normalizer
│   └── rollup-config/     # shared bundling preset
├── packages/
│   ├── shared/            # framework-agnostic IconNode types + builders
│   ├── svg/               # @nubo-icons/svg: optimized SVGs, sprite, nodes JSON, metadata index
│   ├── react/             # @nubo-icons/react (launch target)
│   └── vue/ svelte/ …     # added later from templates
├── apps/web/              # docs + icon browser, imports workspace packages
├── integrations/          # Next.js / Vite smoke apps
└── .github/               # workflows, issue forms, PR template
```

Each icon's JSON sidecar should follow a strict JSON Schema with `additionalProperties: false`. Required fields are `tags`, `categories` (an enum), `contributors`, `addedIn` and a stable `codepoint` (assigned automatically, as Tabler does). Optional fields are `aliases` (each with `deprecated`, `deprecationReason` and `removeInVersion`), `rtl` (`mirror | no-mirror | variant`, following Fluent's `directionType`) and a short `description`. Sidecar JSON is easier to lint, diff and review in PRs than Tabler's front matter or Phosphor's private API. The `rtl` field makes nubo better than Lucide on bidirectional support at almost no cost. Add Octicons-style geometry fingerprints for icons whose glyphs must never change silently. Validate SVGs with a Lucide-style per-element attribute allowlist plus Tabler's structural checks: exact root header, no transforms, no `<g>`, stroke attributes only on the root, three-decimal precision and no degenerate segments. Run the validator as a Prettier check, so the same command fixes files locally and fails them in CI.

For builds, use Turborepo with cache inputs keyed on `icons/**` and `tools/**`, pnpm catalogs, and `minimumReleaseAge`. Use Rollup or rolldown with esbuild to emit **ESM with preserveModules plus CJS, and no UMD**. Generate an `exports` map with `types` first, a `./icons/*` per-icon subpath and a `./dynamic` lazy-import map. Declare `"sideEffects": false`, and check every package with `publint` and `@arethetypeswrong/cli`. Add the hard budget that none of the big three has: a size-limit or tree-shaking test that imports one icon and fails if the output exceeds a few hundred bytes (Octicons already tests tree-shaking). Generated modules should carry Lucide's JSDoc `@preview` image and `@deprecated` tags.

The React API should match Lucide's props (`size`, `color`, `strokeWidth`, `absoluteStrokeWidth`/`nonScalingStroke`, `className`) so that switching costs a find-and-replace on import paths. Export `HouseIcon`-style names, with an optional Lucide-name compatibility map. On accessibility, follow MUI's model and avoid Heroicons' pitfall. Render `aria-hidden="true"`, `focusable="false"` and `data-slot="icon"` by default. When `title` or `aria-label` is passed, switch to `role="img"` with `<title id>` and `aria-labelledby`, and remove `aria-hidden`. Never emit `<title>` from design tools. Keep the per-icon components free of React context, so they render as server components without a `'use client'` boundary, and offer the defaults provider as an optional separate export. This is an inference from Lucide marking its base as a client file and Tabler maintaining a dedicated RSC test app. Expose `mirrored`, or apply mirroring automatically from the `rtl` metadata under `dir="rtl"`.

For releases, use Changesets with every package in one **fixed version group**, and have CI write a changeset automatically whenever icons are added (Tabler's model). Publish through npm trusted publishing with OIDC provenance, behind a protected GitHub Environment, with every Action pinned to a commit SHA. Adopt Simple Icons' versioning policy in writing. Additions are minor, redraws and metadata fixes are patch, and renames or removals are major. Renamed icons stay as `@deprecated` aliases until a scheduled major. Start at 1.0.0 rather than spending years in 0.x as Lucide did. For PRs, use the fork-safe preview pattern: render changed icons in an unprivileged job and comment from a `workflow_run` job. Add a name-parity check across styles that fails the build, unlike Heroicons' advisory one.

### Governance and distribution: curate icons, open the code, ride Iconify and shadcn

Accept code PRs openly, but accept **icons through structured issue forms** (name, use case, references, tags) until the spec has survived a few hundred icons. Design review should stay with a small group of named maintainers, so the project never depends on one person the way Feather did. Require AI-use disclosure on icon contributions, as Simple Icons does. License the set **MIT**, which is the norm and a precondition for Iconify inclusion, and document that glyphs from Remix (since 2026) cannot be used. At launch, ship only `@nubo-icons/svg` and `@nubo-icons/react`, then file the Iconify inclusion request right away. Iconify instantly covers Tailwind 4, unplugin-icons, UnoCSS and Vue/Svelte/Solid users while the native packages mature. Add framework packages through the shared codegen templates only when demand appears, and leave the icon font out until someone asks for it. Make shadcn compatibility an explicit feature, with matching names, props and a documented one-line swap, because the ecosystem already treats "drop-in Lucide replacement" as a selling point ([HN Show HN](https://news.ycombinator.com/item?id=48395648)).

Build the website in `apps/web` as a static-first site that imports the workspace packages. Astro with React islands, or VitePress, both fit. Generate the following at build time from git and the sidecars: per-icon pages (added-in and changed-in versions, contributors, related icons, an RTL note, copy SVG/JSX), OG images, a JSON metadata index and `/stats.json`. Search should use Fuse.js-style weighted matching on name, aliases and tags at a threshold around 0.2, with all query tokens required. Persist customizer and query state in the URL, and add a `/` focus shortcut and `new`/`updated` filters. Virtualize the grid once the set passes about 1,500 visible cells. Two cheap additions would make nubo stand out: an auto-generated `llms.txt`, and an **official MCP server** (search icons, get SVG, get framework snippet), which none of the ten benchmark projects ships.

## Conclusion

The research changes where the effort should go. Icon quality is necessary but it is not what wins. Lucide won with an aesthetic it inherited almost unchanged, and Heroicons holds 4 million weekly downloads with a closed set of about 324 icons. What separates winners from stagnant sets is **written rules enforced by machines, governance that outlives any one maintainer, and a place in the default toolchain**. For nubo-icons, the design work that matters most is small and early: choosing the stroke, the corner rules, the modifier geometry and one signature trait, and then encoding each in a lint rule. After that, the important work is infrastructure: schema-validated metadata, automatic releases, accessible defaults and Iconify/shadcn compatibility.

Two open questions should shape nubo's first months. First, the evidence that familiar icon styles are preferred means every step away from the Lucide look costs some adoption. Nubo's lighter stroke and signature curve should be tested against Lucide in real interfaces before the spec is frozen. Second, the absence of official machine interfaces (an MCP server, structured metadata APIs) across every major set is new in 2026. As more UI code is written by agents that choose icons by searching metadata, rich tags, use-cases and descriptions may matter as much as the drawings, which is a reason to treat nubo's metadata schema as a core part of the product.
